1Executive summary

CallingClaw thinks in two systems: System 1 (S1) — the fast real-time voice model plus two Haiku helpers riding the transcript — and System 2 (S2) — slow, deliberate work (web/deep research, memory recall, screen actions). Every S2 result has to re-enter the live conversation, but there is no contract for how it does so. Five ad-hoc return paths have grown, each with a different injection layer, speech trigger, staleness rule, and dedup. The damage is concrete: a shipped TypeError that makes the AI announce a search failed while the real answer sits unspoken beside it, late answers spoken into dead air, and a loop that can silently go mute for the rest of a meeting because no liveness watchdog exists.

We fix this with one owner. A single VoiceResponseScheduler inside VoiceModule becomes the sole authority over response acceptance, debounce, and disposition; the unified result sink sits on the scheduler (not on today's two uncoordinated gates). Staleness becomes deterministic turn/question leases — a late result is silent by default unless its lease is still open — with the model's "stay silent if irrelevant" reduced to a politeness layer. A connection-lifecycle owner with generation tokens lands before we let watchdogs act, and all three watchdogs ship observe-only first. The shape of the answer, in one line: collapse the gate first, then let the sink promise delivery.

2The problem

The live blocker (shipped today)

P0 · transcript-auditor.ts:671

The research-completion path calls this.voice.client.queuePendingResponse() — a method that does not exist (TS2551; the client only exposes flushPendingResponse()) through a private field (TS2341, voice.ts:52). The result is already injected into Layer 3 first; then in the common non-idle case (AI mid-sentence) the call throws a TypeError, control jumps to the .catch(), and a contradictory "search failed" note is injected next to the real answer. On the next turn the model may read the failure note and tell the user the search failed — while the answer is right there.

It shipped because tsc is not a CI gate and ~379 pre-existing type errors mask new ones.

Consequences fall straight out of the table: inconsistent layer choice, inconsistent speech, only path #4 guards staleness, and no single place enforces "never speak a failure sentinel as fact" (both #5's [Recall via …] strings and #1's error branch leak).

The dual-gate falsehood

Codex proved the sink's delivery guarantees are false on today's two uncoordinated gates (VoiceModule._responseActive + RealtimeClient._isSpeaking/debounce). A result judged "spoken" may only be queued, debounced away, or overwritten — a false-positive disposition. So the gate must collapse before the sink can promise anything.

No liveness floor

Four missing mechanisms let the loop die mid-meeting: mute-forever after a barge-in, an executor lane stuck for the whole meeting, a half-open socket where onclose never fires, and voice.reconnect_failed emitted at callingclaw.ts:1062 with zero listeners. Plus cross-meeting bleed — the transcript reset is dead code (meetUrl is always "").

Generality gap

~30 timing/gating magic numbers scattered as class fields; none in CONFIG, none adaptive to language/provider. S1/S2 logic is welded to the meeting + Meet + prep-brief scenario. Real, but not in the "can mute a live meeting" class — so it is sequenced after the robustness core.

3Architecture: before & after

The whole plan reduces to one visual contrast — five tangled returns through two uncoordinated gates, versus four identical envelopes into one scheduler.

Current state — five paths, dual gate, a blocker and a staleness hole

Five producers, five bespoke return mechanisms, converging on two gates that don't know about each other. Path 1 is the shipped blocker; only path 3 guards staleness; the deep-recall fallback (5) can speak a failure string as fact.

Target state — one envelope, one scheduler, one connection owner

Every producer shrinks to "build envelope, call the scheduler." The scheduler is the only code that touches the client, the context queue, or response.create; the connection-lifecycle owner is the only authority over the socket, and its watchdogs observe before they act.

4The unified contract

Two objects. A lean envelope every producer builds, and a scheduler that owns everything else. The envelope is deliberately small in P1 — codex flagged the full kind/staleness enum set as premature — and grows only when a producer needs more.

The lean envelope (P1 first-cut)

// Deliberately LEAN. Grows in P2+ only when needed.
export interface DeliberateResult {
  id: string;           // dedupe + correlation
  sourceTurnId: string; // the lease anchor
  kind: "research" | "recall"
      | "retrieval" | "action";
  summary: string;      // spoken-ready, never a sentinel
  detail: string;       // L3 inject (sink caps length)
  speakPolicy: "proactive" | "silent";
  error?: string;        // → internal note, never spoken
}
// Later (P2+): documentPath, topicId,
// full stalenessPolicy enum, Stage events.

The scheduler & its dispositions

// SINGLE owner of acceptance, pending-
// replacement, debounce, disposition.
// Producers never touch the client or
// response.create directly.
class VoiceResponseScheduler {
  postS2Result(r: DeliberateResult)
    : DeliveryDisposition;
}

type DeliveryDisposition =
  | "response-requested" // speech TRIGGERED
  | "injected"          // silent inject
  | "dropped-stale"     // NOT injected
  | "dropped-dup"       // already served
  | "no-session";       // → queue / Stage doc
Honest disposition

"spoken" was a lie — it meant "we triggered speech," not "the model spoke." Renamed "response-requested". No claim we can't verify.

No inject-then-drop

dropped-stale now means not injected. Stale detail can't be silently picked up on the next natural turn — the old design injected first, then decided.

No-session ≠ lost

S2 results often finish during a reconnect. Instead of dropping, the scheduler bounded-queues across short reconnects or persists to a Stage document.

The generality proof

A hypothetical 6th capability (say, live term-gloss lookup) writes its fetch, builds one envelope, and calls postS2Result. No new injection code, no response.create, no staleness logic, no dedup, no EventBus wiring, no private access. If adding a producer needs anything beyond an envelope, the contract has failed — that is the acceptance test.

5The reliability layer

Staleness and liveness were the two areas codex judged "hard state problems treated as heuristics." Both are re-grounded on deterministic state, with model judgment demoted to a final courtesy.

Deterministic turn / question leases (the primary control)

Every S2 dispatch attaches to a sourceTurnId, a topicId, and an optional explicit "user asked me to report back" flag. When the result returns, the scheduler checks the lease:

  • Lease still open → proactive speech permitted (subject to the gate).
  • Lease superseded (the turn/topic moved on) → default to silent injection or a Stage/document update. Never a bare proactive trigger.
  • The realtime model's "stay silent if this is irrelevant" instruction is a politeness layer only — a last filter, not the mechanism. Once you call response.create you have already invited output; "stay silent" is a preference, not a protocol guarantee.

Liveness mechanisms — each with one home and one invariant

Liveness / keepalive RealtimeClient A half-open socket is detected and recycled (catches the silent death where onclose never fires). Waits for generation tokens. Keys on expected-inbound after an outstanding request — not global inbound silence (a healthy socket is quiet during a long monologue).
Connection generation tokens

Every reconnect, forced close, watchdog reset, and voice.start() is tagged with the current generation and ignored if stale. This is the hard invariant that "three watchdogs, one socket" needs — without it, "supervisor only after client gives up" is an aspiration, not a guarantee. Codex was explicit: separating who mutates which variable is not the same as a single socket-lifecycle owner.

Observe-first activation

All three watchdogs land in P0 observe-only — they log would-reset / would-recycle with the triggering state, but take no action. They flip to enforce only after the scheduler and generation tokens exist in P1, and after a day of real-meeting dogfood tunes the windows. Prevents a too-tight timeout from truncating a legitimately long response or recycling a healthy-but-quiet socket.

8Risk & rollout

This plan edits the live, latency-sensitive, in-meeting voice path. Every change is judged first on "can it make the AI go silent, mute, or wrong in a real meeting."

Guardrails
  • Observe-before-enforce for every reliability mechanism (mode: "observe" | "enforce"). Ship, watch, tune windows on real meetings, then flip.
  • Restart-storm protection — supervisor has a hard cap + exponential backoff + maxDelayMs; after cap it emits voice.dead and stops. Never runs during an intentional stop().
  • Flag the highest blast radius — the gate collapse (now the foundation of P1) ships behind CONVERSATION_SINGLE_GATE and is A/B'd against the historical "did the action, said nothing" symptom before defaulting on.
  • Scoped tsc gate first — the reason the blocker shipped. Lands as the first commit of P0 so the rest of the work is under the gate.
How each change is verified

Unit-testable without a live session: sink dispositions, turn-lease logic, watchdog fire/clear, supervisor backoff schedule, cross-meeting reset, generation-token staleness, orchestrator timeout freeing _active.

Requires dogfood in a real meeting: barge-in mute recovery, late-answer staleness feel, half-open recovery, gate-collapse behaviour, multi-platform recall. These depend on realtime-model judgment and provider timing and cannot be fully asserted in unit tests.

What we are deliberately NOT doing this cycle

  • Not replacing the Realtime provider abstraction or the 5-layer context model — sound and reusable; we build on top.
  • Not building non-meeting ToolClassifier / ContextProvider implementations — P3, seams only.
  • Not hardening EventBus durability (replay / backpressure / webhook timeout) — P3.
  • Not achieving OpenAI ↔ Gemini reconnect parity for the context queue — P3.
  • Not replacing the auditor's regex fast-lane or Haiku classification — only aligning its confidence threshold (P2).
  • Not a new persistence layer for deliberate results — in-memory; the bounded no-session queue and Stage-doc persistence use what already exists.
